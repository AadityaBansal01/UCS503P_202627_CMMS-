    Weekly Project Progress Journal – College Mentorship Management System (CMMS)¶

    Week 1 – Project Pitch Deck¶

    Created the initial CMMS project pitch deck in both PPTX and PDF formats, covering the problem statement, motivation, and proposed solution.

    • Structured the presentation into four slides: Introduction, Motivation, Problem Statement, and Proposed Solution.
    • Identified three major problems in the existing mentorship process: 1. No centralized scheduling system, resulting in missed or poorly coordinated meetings. 2. No systematic meeting tracking, making it difficult for departments to monitor meeting frequency and outcomes. 3. Uneven faculty workload distribution, with limited visibility into the number of students assigned to each mentor.
    • Defined four core solution pillars: Automated Allocation, Seamless Scheduling, Progress Dashboards, and Continuous Monitoring.
    • Established the initial project scope and design direction, which later formed the foundation of the actual backend modules.
    • Designed a minimalist visual theme using a dark-charcoal and off-white palette with a geometric monogram instead of generic stock imagery.

    Week 2 – Project Proposal¶

    Prepared the complete project proposal in LaTeX and PDF formats, following the prescribed course proposal structure.

    • Organized the proposal into Introduction and Problem Statement, Objectives, Methodology, Feasibility, Timeline, and Resources and Budget.
    • Defined one primary objective and five specific sub-objectives covering mentor allocation, meeting scheduling, dashboards, meeting notes, and administrative visibility.
    • Documented the proposed MERN stack architecture, including React frontend, Node.js and Express backend, and MongoDB database.
    • Divided the implementation into four major modules: Allocation, Scheduling, Meeting Notes, and Dashboards.
    • Defined the development approach using weekly iterations, integration activities, and manual deployment.
    • Established testing and validation criteria, including assignment correctness, meeting completion rate, administrative visibility, and user satisfaction.
    • Made deliberate scope adjustments to meet the 12-week timeline: 1. Replaced automated workload balancing with manual administrator reassignment. 2. Replaced structured progress milestones with a free-text meeting notes feature. 3. Deferred CI/CD pipelines and automated testing for the current development stage.
    • Added Technical, Operational, and Economic Feasibility sections based on the actual project requirements.
    • Reviewed and refined the proposal for consistency, clarity, and formal academic presentation.

    Weeks 3 and 4 – System Design, UML Diagrams and DFDs¶

    Worked on the system design phase and prepared the major diagrams required to represent the CMMS architecture and functionality.

    Use-Case Diagram - Created a UML use-case diagram containing three actors: Student, Faculty, and Department Admin. - Identified and modeled 11 major use cases within the CMMS system boundary. - Included common registration and login functionality for all three actors. - Used appropriate UML relationships to represent mandatory operations, including booking a meeting slot and checking booking conflicts. - Cross-checked the use-case diagram with the DFDs to maintain consistency between functional requirements and data flows.

    Data Flow Diagrams - Created the Level 0 Context Diagram representing CMMS as a single process interacting with Student, Faculty, and Department Admin. - Created the Level 1 DFD by decomposing the system into four modules: 1. Allocation 2. Scheduling 3. Meeting Notes 4. Reporting and Dashboard - Identified four data stores: Users, Assignments, Meetings, and Notes. - Maintained Assignments as a separate data store from Users to distinguish mentor-student relationships from user identity information. - Used standard duplicate-entity notation to maintain diagram clarity and avoid unnecessarily long data-flow connections. - Verified consistency between the system processes, external entities, and data stores.

    Week 5 – Authentication, Database Seeding and Allocation Engine¶

    Completed the authentication module and implemented the initial mentor allocation functionality.

    • Developed the login API using JWT-based authentication and bcrypt password hashing with 10 salt rounds.
    • Encoded user roles in JWT tokens to support role-based route protection.
    • Implemented ProtectedRoute.jsx to prevent unauthorized users from accessing restricted frontend pages.
    • Configured and seeded the database with 25+ mock records consisting of faculty members and student advisees from the CSE department.
    • Developed the mentor allocation engine to match students with faculty members based on their department.
    • Tested the allocation logic and verified 100% correct department matching in the tested records, with no cross-department assignments.
    • Developed the My Mentor page to allow students to view their assigned faculty mentor.
    • Completed Milestone M2 (Allocation Engine) within the planned schedule.

    Week 6 – Scheduling Module, Gantt Chart and Prototype Report¶

    Started the scheduling module and worked on project planning and documentation in parallel.

    • Initiated Phase 3 of development by implementing the faculty office-hour availability API.
    • Started developing the calendar interface to fetch and display available meeting slots.
    • Divided the scheduling workflow into four stages: slot creation, availability retrieval, conflict checking, and meeting booking.
    • Coordinated parallel development of the double-booking prevention logic.
    • Prepared the 12-week Gantt chart covering all six project phases and milestones (M1–M6).
    • Drafted the initial Prototype Stage Report, documenting the system architecture, DFDs, ER diagram, database schema, and API routes.
    • Planned further updates to the report after completion of the remaining modules and testing.

    Post-MST Project Progress¶

    Sequence Diagram and System Interaction Modelling¶

    Worked on representing the internal workflow of the CMMS through UML sequence diagrams.

    • Designed and created the sequence diagram illustrating interactions between Student, Faculty, React UI, Express API, and MongoDB.
    • Represented the complete meeting-booking workflow, starting from faculty availability publication and student slot selection to booking confirmation.
    • Included JWT authentication, role verification, student-assignment validation, and database conflict checking.
    • Modeled alternative scenarios for successful booking and unavailable slots using UML alternative fragments.
    • Included the post-meeting workflow covering meeting note submission, database insertion, and updating the meeting status to completed.
    • Verified the sequence of interactions between frontend, backend, and database components.

    Class Diagram, Collaboration Diagram and Deployment Diagram¶

    Prepared additional UML diagrams to represent the structural, interaction, and deployment aspects of the system.

    Class Diagram - Designed and created the UML class diagram representing the major entities and their relationships. - Modeled User, Student, Faculty, DepartmentAdmin, Assignment, AvailabilitySlot, Meeting, and MeetingNote classes. - Added relevant attributes, data types, methods, and associations. - Represented inheritance relationships between User and its three specialized roles. - Defined relationships and multiplicities between assignments, faculty availability, meetings, and meeting notes.

    Collaboration Diagram - Created the collaboration diagram to represent communication and message exchange between different system components. - Illustrated interactions involved in authentication, mentor allocation, availability management, meeting booking, and meeting-note creation. - Represented the responsibilities of the frontend, backend services, database models, and user roles.

    Deployment Diagram - Designed the deployment diagram to illustrate the proposed application deployment architecture. - Represented the React frontend, Node.js and Express backend, and MongoDB database. - Included communication between the frontend and backend through HTTPS-based REST API requests. - Represented JWT-based authentication and database connectivity through Mongoose. - Documented the proposed hosting arrangement using Vercel, Render, and MongoDB Atlas.

    System Implementation, Execution and Testing¶

    Worked on executing the developed application, verifying its functionality, and validating the implemented modules.

    • Worked on running and integrating the frontend and backend application components.
    • Executed the application and checked communication between the React frontend, Express API, and MongoDB database.
    • Reviewed the implemented backend routes, controllers, database models, and authentication middleware.
    • Prepared and executed functional test cases for major application modules.
    • Tested user registration, login, JWT authentication, and role-based access restrictions.
    • Verified mentor allocation functionality and checked department-wise assignment correctness.
    • Tested faculty availability creation and retrieval of available meeting slots.
    • Tested meeting booking functionality, including slot availability validation and double-booking conflict handling.
    • Verified meeting status updates and meeting-note creation.
    • Checked administrative functionalities, including mentor reassignment and department-level information visibility.
    • Identified and addressed issues encountered during execution and integration.
    • Verified the expected outputs and application responses against the defined functional requirements.

    Integration, Validation and Documentation¶

    Focused on reviewing the integrated system, validating the implemented functionality, and completing the technical documentation.

    • Reviewed the integration of the Allocation, Scheduling, Meeting Notes, and Dashboard modules.
    • Verified the consistency of data exchanged between the frontend, backend APIs, and MongoDB collections.
    • Rechecked authentication and role-based authorization across different user interfaces and API endpoints.
    • Reviewed the prepared test cases and recorded the observed results for the implemented functionalities.
    • Verified the system diagrams against the actual application architecture and implemented database models.
    • Refined the UML diagrams, including the Use-Case, Class, Sequence, Collaboration, and Deployment diagrams.
    • Updated the project documentation with implementation details, database structure, API workflows, and testing activities.
    • Reviewed the overall application workflow to ensure that the implemented features aligned with the original project objectives.

                                         Week 1  Project Pitch Deck

    Built the initial CMMS pitch deck (.pptx + .pdf), covering the problem statement, motivation, and proposed solution.

    Structured the deck as a 4-slide minimalist pitch: Introduction, Motivation, Problem Statement, Solution. Wrote the core framing: mentorship currently runs on informal email/office hours coordination, with three specific failure points no shared calendar (missed meetings), no tracking (departments can't see meeting frequency or outcomes), and no workload visibility (mentee counts skew unevenly across faculty with no way to see it). Defined the four solution pillars: Automated Allocation, Seamless Scheduling, Progress Dashboards, Continuous Monitoring. These later became the system's four actual backend modules almost unchanged, so the early framing held up well. Used a dark-charcoal-on-off-white palette with a geometric monogram mark instead of stock or AI-generated imagery, specifically to avoid the deck reading as templated.

                                                Week 2 Project Proposal

    Wrote the full project proposal (.tex + .pdf), following the course's proposal structure guide section by section.

    Structured it into: Introduction/Problem Statement, Objectives, Methodology, Feasibility, Timeline, Resources and Budget. Objectives: one primary goal plus five specific, action-oriented sub-goals (matching, scheduling, dashboards, meeting notes, admin visibility), matching the SMART framing from the guide. Methodology: architecture and tech stack (MERN React frontend, Node/Express API, MongoDB), module breakdown (Allocation, Scheduling, Meeting Notes, Dashboards), execution/integration approach (weekly iterations, manual deploy), and testing/validation criteria (assignment correctness, meeting completion rate, admin visibility, user satisfaction survey). Made an explicit scope-reduction decision to fit the 12-week timeline: dropped automated workload-balancing in allocation (replaced with manual admin reassignment, since admins can already see mentee counts), dropped structured milestones (replaced with a single free-text meeting note field), and dropped CI/CD plus automated testing for this stage. Documented all three as intentional, reversible scope cuts rather than gaps. Added a Feasibility section (Technical / Operational / Economic), each point tied to something already stated elsewhere in the proposal rather than generic boilerplate. Proofread the whole document to strip informal punctuation (em-dashes used as parentheticals) that reads as AI-generated, replacing each with a colon, comma, or a split sentence depending on what actually fit the meaning.

                              Week 3 and   Week 4  — Use-Case Diagram, DFDs, and Allocation Module

    Split my time between finishing the system design diagrams and starting backend work on the allocation module.

    Use-case diagram

    Modeled 3 actors (Student, Faculty, Department Admin) against 11 use cases inside a CMMS system boundary, following standard UML use-case notation rather than an informal box and line sketch. Added a shared Register / Login use case and connected all three actors to it, since every role needs auth. Used a proper relation from Book Meeting Slot to Check Booking Conflict, to show that conflict checking is a mandatory sub-step of booking, not an optional one — deliberately did not use anywhere it wasn't semantically correct (caught and removed one incorrect relation between two different actors' use cases during review). Cross-checked the use-case diagram against the DFDs afterward and found one inconsistency: the use-case diagram listed "Monitor Faculty Workload" as a distinct admin action, but the DFD only showed one generic "metrics" data flow to Admin. Fixed by splitting the DFD's admin-facing flow into separate Mentorship Metrics and Workload Stats flows so both diagrams agree.

    DFDs

    Level 0 (context diagram): CMMS as a single process, 3 external entities, labeled bidirectional data flows. Level 1: decomposed process 0 into the four real modules (1.0 Allocation, 2.0 Scheduling, 3.0 Meeting Notes, 4.0 Reporting/Dashboard) with four data stores (Users, Assignments, Meetings, Notes). Kept Assignments as its own data store (D2) separate from Users (D1) deliberately — mentor-student pairing is relationship data, not identity data, and conflating the two would mean every reassignment writes to the same table as login credentials. Used the standard "duplicate entity" convention (Student/Faculty/Admin*, marked with the corner-cut notation) on the output side of Level 1, so the return flow arrows from the Reporting process don't have to snake back across the entire diagram to reach the original entity boxes.

                                               Week 5 — Auth, Seeding & Allocation Engine

    Finished login API with JWT + bcrypt (10-round hashing), role encoded in the token so route guards don't need extra DB calls. Added ProtectedRoute.jsx so unauthorized users get redirected before the page loads. Seeded 25+ mock records (CSE faculty + advisees) for testing. Built the allocation engine — matches students to mentors by department. Tested 100% correct, no cross-department mismatches. Built the "My Mentor" view for students. Closed M2 (Allocation Engine) on time.

                                              Week 6 — Scheduling Engine Start + Gantt Chart & Prototype Report

    Started Phase 3: booking system. Built API for faculty to publish office-hour slots. Started calendar UI — fetching/showing open slots first, booking logic next. Split scheduling into 4 steps (create slots → fetch available → check conflict → log booking). Harshveer started on the double-booking conflict query in parallel. Put together the 12-week Gantt chart covering all 6 phases and milestones (M1–M6). Drafted the first version of the Prototype Stage Report (architecture, DFDs, ER diagram, DB schema, API routes) — to be finalized once dashboards and testing wrap up.

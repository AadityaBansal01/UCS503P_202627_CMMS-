
                                             
                                             Week 1  Project Pitch Deck

Built the initial CMMS pitch deck (.pptx + .pdf), covering the problem statement, motivation, and proposed solution.

Structured the deck as a 4-slide minimalist pitch: Introduction, Motivation, Problem Statement, Solution.
Wrote the core framing: mentorship currently runs on informal email/office hours coordination, with three specific failure points  no shared calendar (missed meetings), no tracking (departments can't see meeting frequency or outcomes), and no workload visibility (mentee counts skew unevenly across faculty with no way to see it).
Defined the four solution pillars: Automated Allocation, Seamless Scheduling, Progress Dashboards, Continuous Monitoring. These later became the system's four actual backend modules almost unchanged, so the early framing held up well.
Used a dark-charcoal-on-off-white palette with a geometric monogram mark instead of stock or AI-generated imagery, specifically to avoid the deck reading as templated.
                          
                          
                                                Week 2 Project Proposal

Wrote the full project proposal (.tex + .pdf), following the course's proposal structure guide section by section.

Structured it into: Introduction/Problem Statement, Objectives, Methodology, Feasibility, Timeline, Resources and Budget.
Objectives: one primary goal plus five specific, action-oriented sub-goals (matching, scheduling, dashboards, meeting notes, admin visibility), matching the SMART framing from the guide.
Methodology: architecture and tech stack (MERN React frontend, Node/Express API, MongoDB), module breakdown (Allocation, Scheduling, Meeting Notes, Dashboards), execution/integration approach (weekly iterations, manual deploy), and testing/validation criteria (assignment correctness, meeting completion rate, admin visibility, user satisfaction survey).
Made an explicit scope-reduction decision to fit the 12-week timeline: dropped automated workload-balancing in allocation (replaced with manual admin reassignment, since admins can already see mentee counts), dropped structured milestones (replaced with a single free-text meeting note field), and dropped CI/CD plus automated testing for this stage. Documented all three as intentional, reversible scope cuts rather than gaps.
Added a Feasibility section (Technical / Operational / Economic), each point tied to something already stated elsewhere in the proposal rather than generic boilerplate.
Proofread the whole document to strip informal punctuation (em-dashes used as parentheticals) that reads as AI-generated, replacing each with a colon, comma, or a split sentence depending on what actually fit the meaning.
                              
                              
                              Week 3 and   Week 4  — Use-Case Diagram, DFDs, and Allocation Module

Split my time between finishing the system design diagrams and starting backend work on the allocation module.

Use-case diagram

Modeled 3 actors (Student, Faculty, Department Admin) against 11 use cases inside a CMMS system boundary, following standard UML use-case notation rather than an informal box and line sketch.
Added a shared Register / Login use case and connected all three actors to it, since every role needs auth.
Used a proper relation from Book Meeting Slot to Check Booking Conflict, to show that conflict checking is a mandatory sub-step of booking, not an optional one — deliberately did not use  anywhere it wasn't semantically correct (caught and removed one incorrect  relation between two different actors' use cases during review).
Cross-checked the use-case diagram against the DFDs afterward and found one inconsistency: the use-case diagram listed "Monitor Faculty Workload" as a distinct admin action, but the DFD only showed one generic "metrics" data flow to Admin. Fixed by splitting the DFD's admin-facing flow into separate Mentorship Metrics and Workload Stats flows so both diagrams agree.

DFDs

Level 0 (context diagram): CMMS as a single process, 3 external entities, labeled bidirectional data flows.
Level 1: decomposed process 0 into the four real modules (1.0 Allocation, 2.0 Scheduling, 3.0 Meeting Notes, 4.0 Reporting/Dashboard) with four data stores (Users, Assignments, Meetings, Notes).
Kept Assignments as its own data store (D2) separate from Users (D1) deliberately — mentor-student pairing is relationship data, not identity data, and conflating the two would mean every reassignment writes to the same table as login credentials.
Used the standard "duplicate entity" convention (Student*/Faculty*/Admin*, marked with the corner-cut notation) on the output side of Level 1, so the return flow arrows from the Reporting process don't have to snake back across the entire diagram to reach the original entity boxes.

Week 5 — Auth Pipeline, Seed Data & Allocation Engine Completion

Closed out Phase 2 this week: authentication, seeding, and the allocation engine all went from partial to fully working, which is what let us hit M2.

JWT + bcrypt pipeline: Finished /api/users/login, with bcrypt using 10-round salted hashing on the password field and role claims (student/faculty/admin) encoded directly into the JWT payload so route guards don't need a separate DB lookup per request. Bad credentials return a clean 401 rather than leaking whether the email exists.
Route guards: Built out ProtectedRoute.jsx on the frontend so unauthorized users get redirected before a protected view even mounts, instead of flashing the page and then bouncing them — this was the "Role State Hydration" issue flagged as a lesson learned, so we front-loaded the fix here rather than patching it later.
Seed scripts: Wrote seed data for CSE faculty and advisees — landed at 25+ realistic records, enough to stress-test the allocation engine without it just matching everyone 1:1 trivially.
Allocation engine: Implemented the intra-department focus-area matching algorithm. Verified 100% intra-department match accuracy against the seed set — every student ended up paired with a mentor in their own department, no cross-department leakage.
Mentor Discovery / My Mentor UI: Built the assigned-mentor card view so a student can see their advisor's name, department, and contact info immediately after allocation runs, instead of us having to check the DB manually to confirm pairing worked.
Milestone check: this closes out M2 — Working Intra-Department Allocation Engine, on schedule for end of Week 5.

Week 6 — Scheduling Engine Kickoff

Moved into Phase 3 and started the highest-complexity subsystem in the app: the booking/scheduling engine.

Office-Hours Availability API: Built the initial REST endpoints for faculty to publish bookable time windows (PUT /api/mentors/:id/availability). Kept availability as a formatted string/JSON blob on the Mentor document rather than a separate collection for now, since office hours don't need independent querying outside the parent mentor record at this stage.
Booking calendar UI (started): Began the slot-selection widget on the frontend — scoped it as fetch-available-slots first (filtering out anything already booked) before wiring up the actual booking submission, since getting the "what's actually free" query right is the harder half of this feature.
Design decision: Split the scheduling flow conceptually into four sub-steps early — create slots, fetch available slots, validate conflict-free booking, generate booking log — so the concurrency check (coming next week) has a clean seam to slot into rather than being bolted onto a single monolithic booking function.
Flagged for next week: the actual conflict-detection query (atomic check against mentor + status:"scheduled" + date proximity) and the meeting notes API are still open — Harshveer's picking up concurrency validation in parallel with the calendar UI work.
